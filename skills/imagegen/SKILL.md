# 图片生成与编辑

仅当用户期望获得实际图片，或者要求修改现有图片时，使用 `ly_image` 工具。

用户不需要了解、提及或指定 `ly_image`。工具选择属于 Agent 的内部执行逻辑。

## 待办使用边界

- 纯生图、改图、连续修图和批量出图，除非用户明确要求待办计划，否则不调用 `todo`。直接完成必要的查图、看图、提示词整理、生成及交付；多图仍按下文规则委派 `Image-worker`。
- 会话已有待办时，保留原计划，不为本次图片请求查询、更新、替换或清空待办；上下文压缩后恢复的计划简报也遵守此规则。
- 同时包含开发、文档等工作的混合任务，可以维护整体计划，但不把图片制作内部步骤拆成待办。

## 核心判断原则

调用图片工具之前，先判断用户期望的最终交付物。

- 如果最终交付物是实际图片，执行图片生成或图片编辑。
- 如果最终交付物是文字提示词，只输出文字，不执行图片生成。
- “生成图片”属于图片生成请求。
- “生成图片提示词”属于文字生成请求。
- 即使提示词已经完整并且可以直接用于生图，也不能将其视为用户已经授权生成图片。
- 用户不需要说出具体工具名称，只需要明确表达自己想获得的结果。

## 应当调用图片工具的情况

当用户的自然语言明确表示最终需要一张实际图片时，应调用 `ly_image`。

例如：

- “帮我画一只坐在月球上的猫。”
- “生成一张电影感的城市夜景。”
- “给这个产品做一张宣传图。”
- “把这张照片改成动漫风格。”
- “删除图片中的路人。”
- “把人物衣服改成黑色。”
- “使用刚才的提示词出图。”
- “按照这个 Prompt 生成图片。”
- “开始渲染。”

以上请求的最终交付物都是实际图片。

## 不得调用图片工具的情况

当用户期望的最终交付物是文字提示词、提示词分析或创作方案时，不得调用 `ly_image`。

例如：

- “帮我写一个生图提示词。”
- “生成一段图片 Prompt。”
- “给我一份 Midjourney 提示词。”
- “优化一下这段图片提示词。”
- “把这个提示词翻译成英文。”
- “分析一下这个 Prompt。”
- “给我三个不同风格的生图提示词。”
- “按照这个模板输出提示词。”
- “把这张参考图转换成文字提示词。”

这些请求中的“生成”指生成文字，不是生成图片。

处理此类请求时：

- 只输出用户要求的提示词、分析或文字内容。
- 不得调用 `ly_image`。
- 不得调用其他图片生成或图片编辑工具。
- 不得在输出提示词后自动继续生成图片。
- 不得因为提示词已经足够完整而推断用户希望立即出图。
- 如果当前正在执行一个提示词生成 Skill，应让该 Skill 完成文字交付，不得自动衔接生图流程。

## 会话上下文判断

判断用户意图时，应结合当前请求和会话上下文。

例如：

- 用户先要求编写提示词，随后说“再给我一个暖色版本”，仍然属于提示词任务。
- 用户先获得提示词，随后说“就用第二个生成图片”，此时属于图片生成任务。
- 用户上传参考图并要求“分析它的画面风格”，属于文字分析任务。
- 用户上传参考图并要求“按照这个风格生成一张新图”，属于参考图生图任务。
- 用户上传图片并要求“把背景换成海边”，属于图片编辑任务。

不得因为对话中出现了图片、参考图或完整提示词，就自动认定用户要求生图。

### 连续创作

- 用户已进入生图/改图任务后，“太假了”“树少一点”“最新那个再暖一点”等明确针对成图的修改，表示继续生成修改版；直接执行，不再询问是否出图。若本轮明确说“只出提示词”“先讨论”，遵守本轮范围。
- “说错了，是第一和第五个”只修正对象选择，不清空之前的构图、颜色等有效要求。新要求替换冲突的旧要求，其他约束继续保留。
- 每次整理完整的最终提示词，而非只传一句增量要求。涉及多个方案，分别保留其差异，使用稳定的方案编号和简短版本名作为 `label`。
- 方案编号代表不同创意，版本名代表同一创意的修订。单张图片反复修改时不要每次递增方案号；用户新要 N 个方案时，本组统一编号 1 到 N，回复中的编号与工具 `label` 保持一致。后续“第二个”等指代优先对应最近展示的方案组，不使用生成次数或资产顺序作为方案号。
- 用户要求多张实际图片（包括同时修改多个已有方案）时，调用 `subagent` 的 `action: team`，每张图分配一个 `agent: Image-worker` 任务。公共约束、原始参考图 assetId 与角色、历史方案 assetId 和本轮修订放入 `sharedContext`；每个任务只给简短方向和固定的 `label`。不要由主 Agent 先写完所有完整提示词，也不要直接批量调用 `ly_image`；子 Agent 各自看图、写完整提示词并生成一张。单图仍直接调用 `ly_image`。
- 新方案组固定编号 1 到 N；修订已有方案沿用其编号。按任务顺序汇总结果，不按完成顺序重排。部分失败时保留成功图片，仅重试失败任务，不把失败当作完成。提示词交付仍只写文字，不启动生图子 Agent。
- `Image-worker` 只执行获派的一张图，显式传 `references`（纯文字生图用 `[]`）和 `count: 1`，成功后结束，不再拆分任务。公共要求与本任务方向共同构成完整提示词，不把其他任务的新成图作为隐式输入。
- 每次委派 `Image-worker` 都在 `skills` 中填写父 Agent 本轮实际采用的 Skill 名称（例如 `quill-image-prompt-director-pro`），没有额外 Skill 则传 `[]`，无需询问用户。执行端直接从父级当前可用目录加载 Skill，并传递所选 Skill 的完整规则；用户切换或停用后更新这次选择，不沿用旧任务的选择。把本轮修改、已确认的提示词和方案差异放入 `sharedContext`，让子 Agent 按当前创作要求继续。已有生成任务使用启动时的状态，新一轮任务重新继承。
- 已给定的焦段、比例、数量等直接采用。只有目标确实歧义且无法通过历史或看图解决时才询问；不要把专业判断转成必填问卷。

### 查图、看图与生成输入

- `ly-image-context` 是当前参考图的轻量清单，不是全部图片历史。找不到“原来的第五个”等目标时，使用 `ly_image_context` 查询当前会话；列表包含顺序、标签、路径、消息与提示词摘要，再用 `assetIds` 查询完整提示词。
- 查询返回的 `ordinal` 是资产出现顺序，包含上传图片，不等于用户说的方案编号。根据标签、对话和提示词判断方案身份。
- 恢复或纠正到早期方案时，按该方案的 `assetId` 取回完整提示词，再更新本轮指定的变化。核对文字描述与所传资产属于同一个方案；不要把另一方案的树木位置、主体布局或风格描述混入，即使两者视觉相似。需要合并方案时应有用户的合并意图。
- 尚未看过相关本地图片，或用户指出构图、颜色、位置不对时，先用 `read` 查看目标和基准图片，再判断如何修改。不要仅凭旧提示词断言图片实际画了什么。
- **视觉对照与生成输入分开**：读取某张图只用于观察，不会自动把它选为生成参考。用户要求“从原图重新生成，不要图改图”，通常意味着仍以最初上传图片生成，结合当前方案的完整提示词，不传中间成图；不意味着丢弃全部原始图片。
- “最新方案继续修改”与“回到原图重新生成”是不同输入选择。工具调用应显式传入本轮所需 `references` 和角色，不依赖隐式回退。纯文字新图显式使用 `taskType: generate`。
- 提示词中逐图说明每张输入的用途，例如图1锁定室内主体，图2仅参考建筑风格。内部角色标签不能替代图片模型实际可读的说明。
- 用户要求比较或保持关键构图时，必要时查看生成结果后再交付判断。未核实的视觉结果不能描述为已严格保持。

## 意图不明确时

优先根据以下信息判断：

1. 用户当前请求中明确表达的最终交付物。
2. 用户明确调用或当前正在执行的其他 Skill。
3. 当前对话所处的任务阶段。
4. 最近一轮相关上下文。

如果仍然无法判断用户想要的是图片还是提示词，应先进行简短确认，不得默认调用图片生成工具。

例如：

> 你希望我只输出生图提示词，还是直接生成图片？

## 职责范围

- 本 Skill 负责识别图片生成或编辑意图、整理图片指令、判断参考图角色，以及执行图片生成或编辑流程。
- 应用程序代码负责已发布的模型能力表、结构化界面选项、Provider 网关、任务状态和本地持久化资源。
- 不要在前端代码中重复实现本 Skill 的工作流程。
- 提示词编写 Skill 负责交付文字提示词；本 Skill 不得自动接管提示词任务并继续出图。

## 参数优先级

每个字段应独立按照以下顺序确定：

1. 用户本轮在结构化界面中新做出的明确选择。
2. 用户自然语言中的明确要求。
3. 当前方案已确定的参数及沿用的界面选项。
4. 管理员设置的模型默认值、Provider 默认值。

`Auto` 或未选择的界面选项不属于明确选择。

不得改写模型支持的、用户已经明确选择的参数。

图片比例、分辨率、数量、格式和模型专属选项，应作为结构化工具参数传递，不要隐藏在提示词中。

## 生成与编辑的区别

### 生成新图片

在没有指定编辑目标的情况下创建新的图片资源。

### 参考图生成

根据一张或多张参考图创建新的图片资源。

参考图可以具有以下角色：

- `character`：人物或主体身份参考。
- `style`：画面风格参考。
- `composition`：构图或布局参考。

如果用户已经明确选择了参考图角色，必须保留用户的选择。

如果用户没有指定参考图角色，应结合会话中的图片内容和任务目标，选择最近且最相关的图片资源。

### 编辑现有图片

编辑是对一张已有图片进行修改，必须包含且只能包含一个 `edit-target`。

其他参考图片必须标记为以下角色之一：

- `character`
- `style`
- `composition`

不得将多张图片同时设置为 `edit-target`。

## 非破坏式编辑

不得覆盖输入图片。

每次编辑都必须生成新的 `assetId`，并将原始编辑目标保留为新资源的 `parentAssetId`。

除非用户明确要求改变，否则应保留以下非目标内容：

- 人物或主体身份。
- 原有构图。
- 光线关系。
- 材质和纹理。
- 颜色关系。
- 背景和环境。
- 其他未被用户指定修改的内容。

只修改用户明确要求改变的部分。

## 工具结果处理

`ly_image` 工具会在任务完成后，将生成结果下载到桌面会话的本地目录，然后再返回结果。

回复用户时：

- 使用工具返回的本地文件路径展示图片。
- 确认展示的是已经下载完成的本地资源。
- 工具结果和后续普通对话只引用 `assetId`、本地路径和必要元数据，不得复制或回显图片 Base64 正文。
- 当前请求需要识图、视觉对比或改图时，可按用户自然语言所指的图片主动读取，无需用户再次手动选图；只读取本轮相关图片，不回传全部历史图片。
- 不得依赖 APIMart 临时 URL。
- 不得将 APIMart 临时 URL 当作最终保存结果提供给用户。
